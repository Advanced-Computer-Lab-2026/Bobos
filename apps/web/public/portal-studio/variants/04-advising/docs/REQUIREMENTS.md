**Implementation levels matter:** “Preview” below means an interactive local staff workflow inside the supplied studio, not an API operation. “Connected” means the new React adapter calls the supplied API; contract tests intercept HTTP and therefore do not prove database behavior. “Retained” means the existing project route remains untouched; it is not counted as newly implemented or re-certified here.

## States represented and states not fabricated

Lists support nonempty, no match, cleared filters, selected record, returning with preserved query, role-unavailable and read-only contexts. Each ten-choice group shares these implementations. Detail/draft views support absent preferences, missing components, incomplete draft, probation, pending approval, pending slot change, awaiting payment choice, review-ready, processed and reasoned reopening. Removal requests support pending, approved, rejected, invalid response and already-resolved local state. Connected API views add loading, transport/service error, not-found lookup, authorization error, retry, no alternatives, conflict refresh, cancellation, resolved and withdrawn states.

Not every production status is seeded in the twelve-student preview. In particular, Normal-student Swap Request Open/Completed/Withdrawn/Expired and a complete Deferred to Next Installment / Ready to Process workflow projection are not synthesized as new authoritative engines. The existing real directory is retained, and the account adapter displays the real API’s workflow values when comparing records. Reopened schedules correctly return to internal Draft with a reopening history entry, per R82; the local list does not implement a separate durable Reopened projection. The complete status vocabulary from R6 remains in the manifest’s source rules rather than being silently removed.

Not-started, ready, rejected and processed states are reachable through the relevant preview operations or represented source records; no developer “force state” toolbar, hidden server success or arbitrary advisor status selector is shipped. Test fixtures may construct edge conditions inside the tests only.

## Role boundaries

An Advisor may browse **all advising students** (R50) while staff slot decisions are limited to their assignments (R43). These are different scopes. An Administrator can change account access (R10), but cannot edit advising drafts or receive the academic-history view (R54). A Coordinator can manage membership/assignment and decide mandatory removals. The UI does not grant account activation to a Coordinator merely because the same admin API namespace contains both features. Student-owned schedule, preference and transcript routes remain in the host and are not replaced with staff components.

Client-side checks are usability boundaries, not a security audit. HTTP role/ownership denial must still be enforced by middleware and controllers. UI fixture tests must never be cited as proof of server isolation.

## Non-functional workbook criteria

**Information Architecture:** task-first grouping; titles/filters/results/reader/action hierarchy; no decorative dashboard panels. **Feedback and Responsiveness:** derived results, disabled states with explanations, loading/error/success feedback, credit balance, selected target and post-save refresh. **Navigation is Reversible:** explicit back-to-queue/students/schedules links, filter retention and focus return; not browser Back alone. **Learnability / Visibility:** native Portal vocabulary, labels on mobile fields, exact component/credit/blocker context and explicit consequences. **Efficiency:** filter rails, grouped queues, two-record comparison, next-record reading and stable preferences. **Design for errors:** required notes/reasons, role restrictions, confirmation/cancellation, blocked seats/clashes, retry and conflict refresh. **Satisfaction:** retained Portal identity and restrained, task-triggered artwork; subjective stakeholder assessment remains required. **UI elements / professional appearance:** scoped host tokens, consistent controls, compact table hierarchy, light/dark and responsive arrangements. **Smooth app flow:** sign-out/sign-in/Overview navigation and calendar operation are exercised; untouched prior features are not all re-certified by this test suite.

## Supplied audit gaps remain visible

`docs/group-b-c-requirements-audit.md` reports 14 strict acceptance failures in its own historical run. That number is a source result, **not a test run performed for this package**. Relevant gaps include GPA-only probation detection/stale workflow projection (R59), bachelor accompanying core-course extra activation (R60), substantive removal grounds (R64), concurrent removal decisions (R69), processing despite pending removals, no live revalidation and duplicate concurrent processing/history (R81/R123). Finance reversal gaps are outside ownership.

Local preview checks demonstrate the intended front-end conditions; they do not repair those API defects. No MongoDB, real SMTP, Google account, payment gateway or concurrent last-seat test was executed here. Production package build and full baseline regression are also not claimed. Those are explicit integration acceptance tasks, not hidden “passing” TODOs.
